4.0 Platform rules
 - Webhook mode with secret token (reject requests lacking the exact secret with 403). Register the webhook at startup; request `allowed_updates` that include message, edited_message, callback_query, inline_query, chosen_inline_result, my_chat_member, chat_member, chat_join_request if used.
 - Command prefixes: "/" for everyone (permission checked per command); "!" for Devs only (non-Devs are ignored silently); "." is accepted as an alias prefix only for the commands that had it: .help and .del. Commands accept the "@BotUsername" suffix. In groups with several bots, ignore commands addressed to another bot.
 - ONE command registry: each command declares name, aliases, scope (private/group/both), required permission (everyone, group admin with specific right, Dev), required bot rights, argument grammar, help text. "/" and "!" variants must come from the same registry so behaviour cannot drift. /help and the Mini App guide are generated from the registry (every command appears there).
 - Target resolution for moderation/economy/family commands: reply target first, then text mention, then numeric user ID, then @username if the user is known to the bot. If none: reply with the exact usage line.
 - Permission failures reply with a precise sentence naming the missing right (for example "I need the Delete Messages admin right to do this.") for both the user's and the bot's missing rights.
 - Admin status is checked live (cache <= 15 s, invalidated on chat_member updates). Anonymous admins (GroupAnonymousBot) are treated as admins. Messages sent on behalf of a channel (sender_chat) follow the explicit policy in 4.2.7.
 - Group Devs always pass permission checks except where Telegram itself forbids the action.

4.2 LOCKS, APPROVALS AND PUNISHMENTS (new behaviour — highest priority)
4.2.1 Lock categories (canonical names and aliases)
  all (everything); text (texts); link (links, url, urls); sticker (stickers); photo (photos, pic, pics, image, images); video (videos); file (files, document, documents, doc, docs); gif (gifs, animation); voice (voices, voicemessage, vm); media (photos + videos + files + gifs); biolink (bio, biolinks, bio_link); promotion (promo, promotions, botpromo, botlink, botlinks, antipromo, botads, ads).
  Commands: /lock <category> [action] ; /unlock <category> ; /locks shows every category with ON/OFF and its action. /lock with no argument prints the usage with all categories.
  Each category is independent. /unlock <category> changes ONLY that category. Unlocking "media" does not unlock photo/video/file/gif individually unless the admin names them; /unlock all turns every category off.
  Locks apply to normal members only. Exempt: Devs, group admins/owner (including anonymous admins), and members approved FOR THAT CATEGORY.
4.2.2 Detection rules (must be implemented exactly)
  - text: message has text content that is not a bot command addressed to this bot.
  - link: any `url` entity, any `text_link` entity (hidden hyperlink), any `text_mention` ignored, plain URLs with scheme, t.me/telegram.me/telegram.dog links, `www.` links, bare domains with a known TLD (policy list is configurable, default: common TLDs), links in captions, links in forwarded messages, inline keyboard URL buttons on user-sent via_bot messages. Mentions (@username) alone are NOT links.
  - photo, video (incl. video notes), file (documents that are not animations, plus audio), gif (animations), sticker, voice (voice messages).
  - media: photo OR video OR file OR gif.
  - biolink: sender's Telegram bio contains a link (checked with getChat; cached with TTL; re-evaluated on every message so removal of the link restores speech).
  - promotion: see 4.2.4.
  - Edited messages are evaluated with the same rules as new messages (edited_message updates).
4.2.3 Punishments (configurable per lock category, default = DELETE)
  - Actions: delete | mute | kick | ban. Default is ALWAYS delete. Enabling a lock without choosing an action must NEVER kick or ban.
  - Admin chooses the action with `/lock <category> [delete|mute <duration>|kick|ban]` and in the Mini App (per category).
  - mute: duration 1 minute to 365 days (default 1 hour when mute is chosen without duration; a value below 30 seconds or above 366 days would be treated as "forever" by Telegram, so enforce the range). Kick = ban then immediate unban (the user may rejoin). Ban = permanent until unbanned.
  - delete always happens first, in every action mode. Mute/kick/ban are applied after delete, once per violation burst (use a 10-second de-duplication window to avoid repeating the action for a rapid series of messages).
  - Bot-rights check at configuration time and at enforcement time: delete needs can_delete_messages; mute/kick/ban need can_restrict_members. If a right is missing, the bot posts one actionable notice (rate-limited) and falls back to whatever it can still do (delete-only), never to a harsher action.
  - Never punish: group admins/owner, Devs, the bot itself, approved users for that category, Telegram service accounts (777000), anonymous admin identity.
  - Every enforcement writes an audit-log row (who, category, action, message id, result/error).
4.2.4 Promotion lock (/lock promotion, /lock promo, legacy aliases)
  Purpose: remove promotional links posted by OTHER BOTS, whether or not those bots are administrators, without touching human members' messages and without changing existing human link-lock behaviour.
  - Identify a bot sender via `from.is_bot` (sender is a bot other than this bot). For messages sent by a human via an inline bot (`via_bot` set), the HUMAN's own link/lock rules apply (do not treat the human as a bot); the promotion lock additionally removes a via_bot message only if the via_bot is another bot AND the message contains a promotional link or URL button. Make this a documented admin setting `promotion_scope` = bots_only (default) | bots_and_via_bot.
  - "Promotional link" = a `url` or `text_link` entity, a scheme/`www.`/t.me/telegram.me/telegram.dog URL in text or caption, or an inline-keyboard button with `url` or `web_app` URL. NOT promotional: user mentions (tg://user?id=...), text_mention, plain @username mentions, this bot's own messages.
  - Allow-list: admins can allow specific bots (by @username/ID) or domains to be exempt from the promotion lock (/lock promotion allow @bot, /lock promotion deny @bot).
  - Works for bot admins and non-admin bots equally.
  - TELEGRAM LIMITATION (verified against core.telegram.org/api/bots/bot-to-bot on 2026-11-16): a bot is not sent other bots' group messages unless (a) the message is a command mention addressed to it or a direct reply to its message, or (b) BOTH conditions hold: Bot-to-Bot Communication Mode is enabled in @BotFather for a participating bot AND this bot is an administrator in the group AND Group Privacy Mode is disabled for this bot. At least one of the two bots must have the mode enabled. Therefore:
      * Implement a Readiness Check (Section 4.2.9) that tells admins exactly which prerequisite is missing for the promotion lock.
      * Document the BotFather steps in /docs/SETUP.md and in the Mini App (Locks tab) as a help sheet.
      * Re-verify this limitation during testing with two real test bots and a real test group; report results. Do not claim the lock works until you have observed a bot-sent promotional message being deleted.
      * Add loop protection for bot-to-bot traffic: ignore this bot's own messages, de-duplicate, rate-limit per bot per chat, never reply to other bots' messages.
  - Must not interfere with the human `link` lock: the two locks are evaluated independently; a human link is handled by `link`, a bot link by `promotion`.
  ACCEPTANCE: (1) With prerequisites met, a test bot posting "https://example.com" or a message with a URL button is deleted within 2 seconds; (2) the same text from a human is untouched when only `promotion` is on; (3) with `link` on and `promotion` off, a human link is deleted and a test bot's link is not; (4) a user mention posted by a test bot is not deleted; (5) readiness check reports missing prerequisites correctly in each combination.
4.2.5 Approvals (replaces the old "approve = exempt from everything")
  - `/approve <target> [category ...]` approves the target ONLY for the named categories. Allowed approval categories: text, voice, file, photo, video, sticker, gif. Aliases follow 4.2.1 (voices, vm, files, photos, videos, stickers, gifs, texts). With no category the bot shows an inline keyboard (toggle buttons for the 7 categories) and applies the choice; it must never silently approve everything.
  - `/approve <target> all` is NOT supported. The bot answers that approval is per category and lists the seven allowed categories.
  - Categories outside the seven (link, biolink, promotion, media, all, flood, force-subscribe) can never be approved by /approve; they remain locked for the target. (media is a group of four approvable categories; "approve media" is rejected with a hint to approve photo/video/file/gif.)
  - `/unapprove <target> [category ...]` removes the named approvals; with no category it removes all approvals of that user.
  - `/approved` lists approved users and their categories. The Mini App edits approvals too.
  - `/unlock <category>` acts independently of approvals.
  - Help text and Mini App copy clearly explain: "Approval lets a member bypass the listed lock categories only."
  ACCEPTANCE: approving user U for photo and sticker lets U send photos/stickers while text lock, link lock, voice lock remain enforced against U; /unlock voice unlocks voice for everyone without altering approvals; /approve U all is refused with the correct message.
4.2.6 Lock commands output
  Replies are short, in English, mention the category, the action and the effect. Example format: "Photo lock is ON. Action: delete message." (Do not copy this wording verbatim if you can write clearer wording; keep it unambiguous.)
4.2.7 Special senders
  - Anonymous admins: exempt. Linked-channel automatic forwards (sender_chat is the linked channel, from user 777000): exempt by default; admins may toggle `locks_apply_to_channel_senders`. Other sender_chat posts (a user posting as a channel): treated as a non-admin member subject to locks; punish by deleting (mute/kick/ban of a channel identity uses banChatSenderChat).
4.2.8 Anti-flood, warns (preserve, improve)
  - Anti-flood: window N seconds (default 5), max messages (3-20, default 5), action delete|mute|kick|ban (default delete; mute duration configurable, default 5 minutes). Applies to non-admin, non-Dev members. Config via /antiflood and Mini App.
  - Warns: /warn increments; reaching warn_limit (0-15; 0 = never act) triggers warn_action mute|kick|ban (default mute 1 hour); /unwarn, /clearwarns, /warns. Warn counts are persistent per chat+user.
4.2.9 Readiness Check (new)
  `/readiness` (admins) and Mini App panel show a checklist for the current group: bot is admin; can_delete_messages; can_restrict_members; can_invite_users; can_pin; privacy mode state; whether chat_member updates are flowing (observed within the last 24 h); Bot-to-Bot mode state if detectable (otherwise "cannot be detected; verify in BotFather"); force-subscribe channel access. Each failing item has a fix hint.
 ACCEPTANCE for 4.2 overall: automated tests with a Telegram API mock for every category x action x exempt/not-exempt combination (matrix test), plus a manual test script executed on a real test group and recorded in the test report.

4.3 FORCE SUBSCRIPTION / CHANNEL VERIFICATION (new)
 Purpose: admins require members to be in a configured channel before they can talk in the group.
 Configuration (per group; Mini App + commands /forcesub on|off, /setforcesub <@channel|-100id|invite link>, /forcesubaction <delete|mute <duration>|kick|ban>, /forcesubstatus):
  - required channel (public @username or private numeric ID plus invite link shown to users), enabled flag, action (default DELETE), mute duration (default 1 hour when action is mute), exempt list (admins and Devs always exempt; admins may add exempt users), announcement mode (silent | short notice with Join and "I have joined" buttons, notice auto-deleted after 15 s, rate-limited to one per user per 60 s).
  - At configuration time verify: channel exists; the bot is a member/administrator of the channel (Telegram only lets a bot read member lists of a channel when it is an administrator there); the bot can call getChatMember on the channel. If verification fails, do NOT enable enforcement; tell the admin exactly what to fix.
 Membership verification:
  - Use getChatMember(channel_id, user_id). A user counts as subscribed if status is member, administrator, creator, or restricted with is_member = true. left, kicked, restricted with is_member = false = not subscribed.
  - Cache positive results for up to 10 minutes and negative results for up to 20 seconds; invalidate on chat_member updates from the channel (if the bot receives them) and when the user presses "I have joined".
  - Rate-limit and queue Telegram calls to respect Telegram flood limits; coalesce parallel checks for the same user.
  - Telegram-API-failure policy (documented, default FAIL-OPEN): if Telegram returns an error that is not "user not found/left" (timeouts, 5xx, 429, bot removed from channel, channel made private), never punish the user; notify group admins once (rate-limited) that verification is failing; auto-pause enforcement after 5 consecutive failures within 10 minutes and tell admins. Admins may switch to fail-closed in the Mini App (delete only, never mute/kick/ban on API failure).
  - Users who never started the bot are verified without DM (getChatMember works without DM).
 Enforcement:
  - Applies to every message type from non-exempt members (text, media, stickers, voice, etc.), to edited messages, and to join events if the admin selects "check on join".
  - Actions follow 4.2.3 semantics: delete always first; mute/kick/ban only if the admin selected them; defaults to delete.
  - After a user presses "I have joined" and verification succeeds, remove any force-subscribe mute applied by this feature (restore previous permissions) and clear the notice.
  - Audit-log every enforcement; per-group counters visible in the Mini App.
 ACCEPTANCE: test matrix (not subscribed/subscribed/left/restricted-member/restricted-non-member x delete/mute/kick/ban x API ok/API failing); proof that default config deletes only; proof that a failing Telegram API causes zero punishments; proof that exempt users are untouched; real-group test with a real private and a real public channel, recorded.

4.6 ECONOMY, XP, PROFILE, KILL SYSTEM (preserve the documented rules)
 - Wallet in coins per user ID; Devs have infinite coins (displayed as infinity), can /give any amount without losing coins, cannot be robbed but can be killed and revive for free; the bot (Avni) is the sink for rob fines and can never be killed or robbed. All balance changes go through a ledger (immutable rows) inside DB transactions; balances can never become negative; concurrent operations are safe.
 - XP: level n requires 50 * n * (n - 1) total XP. Win XP 50, kill XP 25, rob XP 20 (constants configurable).
 - /kill: killer gets 100 coins; victim is dead in every group for 24 hours; dead users cannot be killed again, cannot kill, protect or rob; the system tells them to /revive. /revive costs 200 (payer is the person who ran the command; Devs free); auto-revive at 24 h (persisted deadline, survives restarts). /protect costs 200, 24 h immunity from kill/rob, not available to dead users. /rob AMOUNT: max 5,000, takes what the victim has if less, cannot target protected/dead users, 20% chance of being caught: fine 10% of the attempted amount (if the robber has less, all) paid to the bot, plus 3-minute rob jail (blocks only rob). /open and /close toggle the kill system per group (admins and Devs). Messages in clear English.
 - Profile: coins, XP, level, rank, status (alive/dead/protected), game stats per game, achievements, 30-day trend (wins, coins, XP, games), optional custom title unlocked at configurable level (default 3).
 - Leaderboards: coins, XP, competitive wins, per game. Pagination and caching with 30-second TTL.
 ACCEPTANCE: property/concurrency tests on the ledger (no negative balances under 100 parallel operations), unit tests for each rule above, restart test for deadlines.

6. GAME PLATFORM (shared by every game)
================================================================================
6.1 Principles
 - Server-authoritative: clients send intents (move, roll, shot, input), the server validates against the rules engine and broadcasts state. Clients never decide outcomes.
 - Each game has a pure, deterministic rules engine in `packages/shared/games/<game>` with exhaustive unit tests; the server runs it; the client may run it for prediction/validation of UX only.
 - Real-time transport: WebSocket (JSON or MessagePack; choose by ADR and benchmark). Messages carry `roomId`, monotonically increasing `seq`, and a `serverTime`. Reconnect with resume token; the server replays missed events or sends a full snapshot. HTTP REST remains for non-real-time operations.
 - Persisted state: rooms, players, moves/events and results live in Postgres (Section 12). Active-room hot state may live in memory but every turn boundary and every deadline is persisted so a restart restores the room and its timers.
6.2 Room lifecycle and seating
 - States: lobby -> countdown -> playing -> (paused for disconnect) -> finished | cancelled | expired.
 - Create: host picks game, options (6.5), visibility (invite-only default). Invite via deep link `https://t.me/<bot>?startapp=<token>` and via in-chat share button; token is random 128-bit, single room, expires with the room. Joining from the Mini App opens the lobby directly.
 - Seats are dynamic: the room shows exactly the seats allowed by the game and chosen player count (Chess 2, Tic-Tac-Toe 2, Ice Hockey 2, UNO 2-4 plus bot seats, Ludo 2-4, Carrom 2 or 4 (singles/doubles), Scrabble 2-4). Seat layout is drawn around the central board/table (UNO and Ludo: players around the table; Chess/Hockey: opponent at top, you at bottom; Carrom: players on the board edges). A seat shows avatar (Telegram photo if available, otherwise generated monogram), name, status chip (host, ready, connected, disconnected, bot).
 - Host controls: choose options, add/remove bots, kick a player (before start), set ready state rules (all humans ready), start. Guests: ready/unready, leave. Host leaving a lobby cancels or transfers host (transfer to the longest-waiting human; cancel if none) — specify chosen behaviour in UI copy.
 - A user may be in at most one active room per game type (and at most 2 rooms overall, configurable); trying otherwise offers "return to your game".
6.3 3-2-1 synchronized countdown
 - When the host starts (or all ready), the server sets `countdownStartsAt = serverNow + 500 ms` and `playStartsAt = countdownStartsAt + 3000 ms` and broadcasts both. Clients render 3, 2, 1, GO from the server clock offset (6.4) so every player sees the same number within +/- 100 ms. No input is accepted before `playStartsAt` (server rejects with a clear reason; hockey/carrom controls remain visibly locked).
 - If any human disconnects during the countdown, the countdown pauses up to 10 s, then aborts back to lobby with the reason.
 - ACCEPTANCE: automated test with 4 simulated clients with different clock skews (+/- 5 s) and latencies (30-250 ms) shows the visible "GO" within 100 ms of each other (measured by server-time stamps); manual test on two real phones recorded.
6.4 Clock and timers
 - On connect the client runs 5 ping/pong samples to estimate `offset` and RTT (take the median of the lowest-RTT samples), refreshes every 30 s, and renders ALL countdowns from `serverNow = Date.now() + offset`.
 - Game timer (match clock, chess clocks, per-turn timers) are server deadlines (`deadlineAt`). The UI only displays; drift must never decide a result. Display precision: seconds for turn timers, tenths when under 10 s for chess.
 - Accurate countdown requirement: displayed remaining time within +/- 250 ms of the server's value at all times under normal network conditions; test with throttled CPU.
6.5 Options per game (only these; do not add others)
 - All games: player count/seat count, bots (where supported, 6.6), turn timer preset (Off, 15 s, 30 s, 45 s, 60 s where the game has turns), "private" invite code.
 - Chess: time control presets (Untimed, 3+0, 5+0, 10+0, 15+10, 30+0), colour (random/white/black), vs AI level (6.6), takebacks off by default.
 - Tic-Tac-Toe: first mover (random/host), best-of 1/3/5.
 - UNO: players 2-4, bots 0-3 (total seats <= 4), turn timer (default 45 s), rule set fixed as in 7.4.
 - Ludo: players 2-4 (humans + bots), turn timer (default 30 s), three-sixes rule on/off (default on).
 - Carrom: singles (2) or doubles (4), board/bot options, shot timer (default 45 s).
 - Ice Hockey: score target (3/5/7) or timed (2 or 3 minutes), default first to 5 plus a 3-minute cap with sudden death.
 - Scrabble: players 2-4, turn timer (Off, 1, 2, 3 minutes per turn), challenge mode (on/off, default on).
6.6 AI bots
 - Selectable for UNO, Ludo and Carrom: the host chooses how many bots (any number such that humans + bots fit the seat limit; examples: UNO 1-3, Ludo 1-3, Carrom 1 in singles or up to 3 in doubles) and a difficulty (Easy, Normal, Hard). Several bots may play in the same room. Bots have names/avatars from a neutral list written by you (not personas from the personality file), are labelled "BOT", move after a human-like delay (500-1,500 ms, configurable), never see hidden information they should not know (UNO hands, Scrabble racks), and obey the same rules engine.
 - Chess keeps AI levels (Beginner, Casual, Club, Strong, Expert) using a real engine (for example Stockfish compiled to WASM/Node or a native binary) with documented skill/depth mapping; document that levels are approximate. Tic-Tac-Toe vs AI: Easy (random with blocks), Normal, Hard (perfect play). Ice Hockey and Scrabble bots are NOT required (do not build unless the owner asks; see Section 20).
 - Bot-only or bot-heavy matches: coin rewards obey the anti-farm caps in 6.8.
6.7 Common controls
 - Leave: before start = leave seat; during play = confirm dialog "Leaving forfeits your seat"; for 3+ player games the remaining players continue (a bot may take over the seat if the host enabled "bot replaces leavers"; default on for UNO and Ludo).
 - Resign (2-player games and Carrom doubles team captain): confirm dialog, immediate loss for the resigner.
 - Disconnect handling: grace period 60 s (30 s in hockey); turn timers keep running; if the grace expires the player forfeits (2-player) or is replaced/skipped per game rules. On reconnect the client receives a full snapshot and resumes.
 - Pause: not offered, except automatic pause during countdown disconnects.
 - Draw offer and rematch: chess (draw offer), all 2-player games (rematch request with acceptance).
 - In-room quick reactions (emoji set of 6) rate-limited; no free-text chat (reduces moderation burden) unless the owner requests it.
6.8 Results, rewards, stats
 - On finish the server writes the result (winner(s), placements, reason), updates stats, pays rewards, and posts a result card into the origin Telegram chat when the room was started from a chat (as the old product did).
 - Rewards: win = 100 coins + 50 XP (constants configurable). Matches that include bots: coin reward only for matches with at least one other human OR subject to a daily cap of 300 coins from bot matches and a 45-second cooldown between paid bot matches; XP from bot matches off by default. Rewards are written through the ledger idempotently (one reward per match per player).
 - Stats: played/wins/losses/draws per game, streaks, competitive wins (matches with >= 2 humans), 30-day daily snapshot for trends, achievements (design a list of at least 12 achievements across games; document in /docs/ACHIEVEMENTS.md).
6.9 Anti-cheat and integrity
 - Hidden information is never sent to clients that must not see it (UNO hands of others, Scrabble racks of others, draw pile order).
 - Rate-limit intents per socket; validate all numeric ranges (shot power, positions, striker coordinates) against the board geometry; clamp and reject impossible values; per-room sequence numbers prevent replay.
 - Hockey/Carrom physics outcomes are computed on the server (6.x game sections).
6.10 Mini App game UI wrapper (common to all games)
 - Full-screen game stage with: top bar (back/leave, room name, match timer), seat HUDs, central board, bottom action area, toast area, reconnect banner, countdown overlay.
 - Prevent accidental closing during live games: call the Mini App API to disable vertical swipes and enable the closing confirmation while a match is live (verify the exact method names in the current Telegram Mini App docs at implementation time) and re-enable on exit. Use fullscreen where supported and appropriate.
 - Sound and haptics: optional, off-by-default for sound, on-by-default for light haptics; toggle in settings; all sounds are royalty-free assets that you create or properly license and list in /docs/CREDITS.md.
 ACCEPTANCE for 6: protocol conformance tests (client/server schema), reconnect/resume tests, deadline-survives-restart test (kill the server mid-match, restart, match resumes with correct remaining time), countdown test (6.3), property tests for seating/host transfer, load test (Section 17.6).

7.3 ICE HOCKEY (air-hockey style on an ice rink)
 Reference quality: polished, responsive mobile ice-hockey game. Do not copy another product's art.

 CONTROL REQUIREMENTS (critical): the player's striker must follow the finger immediately and smoothly with NO noticeable input delay or lag.

9. AI CHAT AND THE EXTERNAL PERSONALITY FILE (Personality Engine)
================================================================================
9.1 Source of truth
 - The owner provides ONE text file (for example `personality.txt`). It is the ONLY source of the AI character: identity, tone, language, habits, boundaries, predefined responses and special-case instructions.
 - Place it at `config/personality/personality.txt` in the GitHub repository. Filename and path are configurable with env `PERSONALITY_FILE` (default as above). The application source must contain NO personality text, NO character name used for behaviour, NO sample replies, NO per-trigger canned strings. (Technical error messages that are not part of the character are allowed and must be neutral and in English.)
9.2 Loading, validation, reload
 - Read at startup and cache in memory with SHA-256 checksum and byte size. Validate: file exists, UTF-8, non-empty, size within a configurable ceiling (default 200 KB; warn above 40 KB because it costs tokens on every request), no NUL bytes.
 - If the file is missing/invalid at startup: the bot and all non-AI features still start; the AI module starts in DISABLED state; AI addressed messages get one neutral English notice ("Chat is temporarily unavailable") rate-limited per chat; an error is logged and shown in the Dev dashboard. Never fall back to an invented persona.
 - `!reloadpersonality` (Dev only) re-reads the file, validates, atomically swaps it in, logs checksum old -> new, and reports the result. A failed reload keeps the last good version and says so.
 - Updating through GitHub: the owner edits the file in the repo and pushes; Render autoDeploy redeploys; optionally the Dev runs !reloadpersonality after a deploy that did not restart the process. Document this flow in /docs/PERSONALITY.md. Add a CI check that fails if the file is missing or empty.
 - Expose the active checksum and load time in /api/version (Dev-only detail) and in `!devhelp`.
9.3 Prompt assembly
 - System message = a thin technical wrapper (written by you, persona-free: instructs the model to follow the supplied specification exactly, to prefer explicitly specified responses verbatim, and to keep within the platform's safety limits) + the full personality text verbatim. Do not paraphrase, shorten, translate or "improve" the personality text. If the file is too large for the model context, truncate NOTHING silently: fail validation with a clear error.
9.4 Predefined-response handling (fixes the old "generic refusal instead of the configured answer" defect)
 - When you receive the personality file, read it completely and extract every place where it defines a predefined response, canned line, trigger/response pair, special-case instruction, boundary reply, fallback reply, or language rule. Produce /docs/PERSONALITY_RULES_MAP.md listing each with its exact text location (heading/line number) and your interpretation. Ask the owner to confirm the map before building the matcher if any item is ambiguous.
 - Implement a deterministic Trigger Layer that runs BEFORE any LLM call: detect triggers (normalised text: case-folding, Unicode normalisation, repeated-letter collapsing, punctuation/emoji tolerance, common short-form expansion drawn ONLY from the personality file if it defines them) and, when the file specifies a literal response, return that response as written. When the file specifies a behaviour instead of a literal line, pass an explicit "specification priority" note and the matched rule text to the model, and verify post-generation that the answer follows the rule when the rule is checkable (for example required phrase present).
 - If the file does not give machine-detectable triggers, do not invent any. Instead keep the file authoritative in the prompt and ask the owner whether they want a sidecar `personality_triggers.json` (derived 1:1 from the file, without altering the personality text) — do not create it without approval.
 - Refusal handling: NEVER replace a model answer with a generic refusal because it matches a regex. Detect provider-side refusals only through provider metadata (finish reason / safety flags / empty content) or an explicit refusal classifier with tests. When a provider refusal happens: (1) retry once with the specification-priority note; (2) if the file defines a response for that situation, send it; (3) otherwise send the neutral English technical notice. Log the event with category (never log full user text).
 - Safety layer (platform-level, persona-independent): self-harm/crisis messages receive a supportive neutral response regardless of persona (message text configurable in a platform file separate from the personality file); sexual-explicit and hateful content boundaries follow the personality file where it defines them, with a platform minimum that never generates explicit sexual content.
 - Language: reply language follows the personality file. Command replies and game messages stay English (R9).
9.5 Chat behaviour (functional, persona-free)
 - Groups: reply only when the bot is named (name set in config `BOT_DISPLAY_NAME`), @mentioned, or its message is replied to; never reply to other bots; respect /chatoff. DMs: always reply. Show typing action. Per-chat memory of the last 10 messages (user + assistant), persisted per chat with 7-day TTL; /reset clears it. Multi-user groups prefix speaker names. Keep memory out of logs.
 - Providers: Groq-compatible chat API behind an `AiProvider` interface with timeouts (default 20 s), retry with backoff, circuit breaker, model fallback list from env (`AI_MODELS`), per-chat concurrency limit of 1, global concurrency cap, and token/max length limits from env. Provider API key only from env.
 - Management-intent text sent in DM ("change welcome", "lock links") gets a button to the Mini App group dashboard instead of an AI answer.
 ACCEPTANCE (all automated with a mocked provider): (a) for every trigger in PERSONALITY_RULES_MAP the exact predefined response is returned and the provider is not called when a literal response exists; (b) a mocked provider that returns "I'm sorry, I can't help with that" never reaches the user as a generic refusal; (c) missing/empty/oversized/non-UTF-8 file -> AI disabled, other features alive, correct notice; (d) reload swaps atomically and a bad reload keeps the old version; (e) grep test proves the source tree contains no persona strings from the personality file.
